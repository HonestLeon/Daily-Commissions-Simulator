## 2. P0 阻断问题

### P0-1 切换便签会取消上一张便签的待保存编辑

**位置**

- `src/components/NoteEditor.tsx:85`（唯一的 `saveTimer` ref）
- `src/components/NoteEditor.tsx:136-160`（`handleChange`；`:142` 无条件 `clearTimeout`）
- `src/components/NoteEditor.tsx:115-133`（`activeId` 变化只加载新内容，不 flush 旧内容）

**机制**

1. 在便签 A 里输入，`handleChange` 起一个 500ms 的保存定时器，闭包里带着 A 的 `activeId` 和内容。
2. 在 500ms 内切到便签 B。`NoteEditor` 不清理也不立即执行这个定时器，只是加载 B 并把编辑器内容替换成 B。
3. 在 B 里打出第一个字时，`handleChange` 执行 `clearTimeout(saveTimer.current)`，把 A 的定时器取消。
4. A 的最新内容只存在于已经被卸载的旧编辑器里，磁盘上仍是上一次保存的版本，没有任何地方再把它写回。

**后果**

- 用户“改两下 A → 立刻点 B → 接着改 B”就会丢掉 A 的最后一段编辑，且没有任何提示。
- 这是确定的数据丢失路径，不是理论竞态：只要 B 的第一次输入发生在 A 的 500ms 防抖窗口内即可。
- 相关但独立的问题：`hasPendingEdit` 与保存状态也是单例的，切换时旧保存完成会把新便签的标记清掉（见 P2-14）。

**建议**

- 在 `activeId` 变化的 effect 里先把旧便签的 `markdown` 立即 `save_note` 落盘，再加载新便签；或把定时器改为按便签 id 管理的 `Map`，切换时不取消其他便签的定时器。
- 给这条路径加一个可重复的手动测试项（见 6.3 节），未来可考虑对 `NoteEditor` 的防抖逻辑补单元测试。

**状态**：静态确认；未做 UI 自动化复现。

### P0-2 没有单实例保护，两个进程同时读写同一份数据

**位置**

- `src-tauri/src/lib.rs:2641-2729`（`run()` 只注册了 window-state/opener 插件，没有单实例插件或互斥量）
- `src-tauri/Cargo.toml`（依赖里没有 `tauri-plugin-single-instance`）
- 共享资源：`config.json`（`lib.rs:776-875`）、`notes_index.json`（`lib.rs:46-67`）、`notes/<uuid>.md`、`config.json.tmp`、window-state 文件、托盘

**机制**

- 应用没有阻止第二次启动。`--startup`（登录自启）和用户双击桌面图标可以同时得到两个进程；更新器启动新版本时也可能短暂出现两个进程。
- 两个进程都执行 `init_daily`、都写 `notes_index.json` 和 `config.json`。这些写操作没有跨进程锁，`write_config_atomic` 还共用固定的 `config.json.tmp`。

**后果**

- 两个进程可能各自创建一份“今天的每日委托”，随后索引互相覆盖，出现孤儿 `.md` 或当天多份委托。
- 结算的“读索引 → 改 settled → 读配置 → 加余额 → 写配置”交错时，余额可能被覆盖或重复加；`notes_index.json` 可能被截断（叠加 P0-3）。
- 两个托盘图标、两套全屏轮询/动画；`npm run tauri dev` 与正式版共用数据目录时同样会触发（AGENTS.local.md 已提示）。

**建议**

- 引入 `tauri-plugin-single-instance`，第二次启动只把已有主窗 reveal 出来并退出；或在 `setup` 用命名互斥量（`CreateMutexW`）做进程级互斥。
- 在单实例之外，仍建议给索引和配置加锁/原子写，作为纵深防御。

**状态**：静态确认。

### P0-3 `notes_index.json` 非原子写、无备份，损坏后会被自动创建覆盖

**位置**

- `src-tauri/src/lib.rs:53-61`：`read_index` 对读取失败和 JSON 解析失败一律返回空数组。
- `src-tauri/src/lib.rs:63-67`：`write_index` 直接 `fs::write`，没有临时文件、没有 `.bak`。
- `src-tauri/src/lib.rs:443-451`：`auto_create_daily` 看到“今天没有委托”就创建。
- `src-tauri/src/lib.rs:92-96`、`:616`：委托 `.md` 本身也是裸 `fs::write`。

**机制**

- `config.json` 有原子写和 `.bak`，但索引没有。断电、崩溃、杀软截断或跨进程并发写入都可能留下截断的 JSON。
- 下一次启动：`read_index` 解析失败 → 返回 `vec![]` → `auto_create_daily` 认为今天没有委托 → 创建新便签 → `write_index` 用“只有一条新记录”的数组覆盖损坏文件。
- 原 `.md` 文件还在 `notes/` 下，但索引里已经没有它们的 id/标题/日期/结算标记，侧边栏也不会再显示。

**后果**

- 一次损坏就可能让用户**全部历史委托从界面上消失**；原石/摩拉/连续周数还在配置里，但已结算标记丢失，重新触发结算时可能重复计奖。
- 强杀进程时正在写的 `.md` 也可能被截断，造成单篇内容丢失。

**建议**

- `write_index` 改为与 `write_config_atomic` 同样的临时文件 + `sync_all` + 备份方案，并保留上一代 `.bak`。
- `read_index` 解析失败时不要静默返回空：先尝试 `.bak`，再尝试从 `notes/*.md` 重建最小索引（UUID 文件名 + 文件时间 + “每日委托”标题），并把结果备份原文件。
- 委托 `.md` 写入也走原子写（tmp + rename）。

**状态**：静态确认。

## 3. P1 高优先级问题

### P1-1 跨午夜不结算、不创建新委托

**位置**

- `src/App.tsx:51-102`：`init_daily` 只在组件首次挂载的 boot 里调用一次。
- `src/stores/noteStore.ts:541-552`：`initDaily` 没有日期判断。
- `src-tauri/src/lib.rs:466-480`：`init_daily` 负责结算 + 创建今天委托。
- 代码里没有任何跨午夜定时器或日期变化检测（已用 `grep` 确认）。

**机制**

- 应用是托盘常驻 + 开机自启设计，用户完全可能连续数天不退出。
- 只要进程不重启，`settle_previous_note` / `auto_create_daily` 就不会再执行；跨过 0 点后，侧边栏仍停留在昨天，`get_today_progress` 找不到“今天”的便签，宠物动作/提醒也基于旧数据。
- `check_weekly` 只按当前时刻所在的自然周统计，如果运行跨周，也要等到下一次点击才更新。

**后果**

- “每日委托”这个核心功能在“一直开着”的常见使用方式下失效：没有新委托、没有结算、没有原石/摩拉入账。
- 用户在昨天那份便签上继续勾选/编辑，可能把昨天的数据带到今天，之后在下次启动时被当作“前日委托”结算，语义混乱。

**建议**

- 在 `App` 里加一个轻量的日期巡检（例如每 30–60 秒比较 `today_ymd`，或在窗口 focus / 系统 resume 时检查），日期变化时重新执行 `fetchUiState`/`initDaily`/`fetchNotes`/`fetchProgress`。
- 更稳妥的做法是把“今天”的判断放到 Rust 的 `get_today_progress` 之外，另加一个 `ensure_today` 命令，由前端在日期变化时调用；注意与结算幂等性配合。

**状态**：静态确认。

- `src-tauri/src/lib.rs:618-627`：`save_note` 只要内容变化就刷新 `updated_at`。

**机制**

- 用户打开一份很久以前的每日委托、改一个字，它的 `updated_at` 就变成现在，成为“最近更新的便签”。
- 下一次启动时：
  - 结算选中这份旧便签（而不是昨天那份），把它标成 settled 并结算它的内容；昨天那份反而继续处于未结算状态。
  - 如果旧便签不是每日委托（例如历史遗留的非模板便签），它会以 0 奖励被 settled，并阻塞昨天的结算。
  - 次日的继承同样从这份旧便签取内容，导致“今天”的任务来自任意旧日期。

**后果**

- 原石/摩拉结算对象错位、到账延迟或遗漏；`settled` 标记被写到不该写的便签上。
- 每日委托的继承内容错乱，用户会以为应用“复制错了昨天”。

**建议**

- 选取依据改成 `created_at`（日期），并按“最近的、早于今天的、包含每日委托模板的便签”过滤；不要用 `updated_at` 判断业务日期。
- `settle_previous_note` 最好一次结算所有已过期的未结算每日委托（或至少明确只结算“昨天”），并用单独的字段记录结算日期，避免一次启动只结算一份造成的积压。
- 为“旧便签被编辑后不会影响结算/继承”补一个纯函数单元测试。

**状态**：静态确认。

### P1-3 周挑战连击逻辑：周中查看会提前清零，跳过整周却不会清零

**位置**

- `src-tauri/src/lib.rs:500-518`：`weekly_settle_logic`。
- `src-tauri/src/lib.rs:559-572`：`check_weekly` 在 `already == false` 时无条件保存结果。
- `src/components/LixingDialog.tsx:61-90`：用户看到“本周未达标，砺行连续周数已清零”。

**问题 A：周中查看会提前清零**

- 用户周一/周二点开“砺行修远”只是想看进度，`count < 5`、`already == false` → `weekly_settle_logic` 返回 `streak = 0`，`check_weekly` 立即 `save_config`。
- 这周后面即使完成 5 天，也只能拿到 `100 * (0 + 1)`，之前积累的连续周数已经丢了。
- 现有单元测试 `weekly_settle_is_idempotent_across_calls` 本身就断言了 `weekly_settle_logic(3, 5, false) = (false, 0, 0)`；纯函数行为没问题，错在**查看按钮直接执行了“结算”**。

**问题 B：跳过的周不会清零**

- `weekly_settled_week` 只在“达标发奖”时写入，代码没有比较“上一个已结算周是否就是上周”。
- 用户连续第 1 周达标后，第 2 周完全不打开应用；第 3 周达标时 `already == false`，直接 `streak + 1`，连续周数把中间失败的一周也算了进去。
- README 写的是“中断（某周未达标）→ 连续周数清零”，实现没有覆盖“未打开应用的那一周”。

**问题 C：显示与状态可能不一致**

- 如果本周已经发奖（`already == true`），之后用户删掉了部分任务导致当前 `count < 5`，`weekly_settle_logic` 返回 `eligible = false` 但 `streak` 不变；弹窗的失败分支却固定显示“砺行连续周数已清零”。状态没清，文案说清了。

**建议**

- 把“查看进度”和“结算本周”拆成两个动作；或者只在周日/下周一允许失败清零，查看时只读。
- 增加 `weekly_last_checked_week` / `weekly_last_settled_week` 语义：如果当前周不是上次记录周的下一周，先把 streak 清零再计算。
- 弹窗文案以返回的 `streak` 为准，不要假定“未达标 = 已清零”。

**状态**：静态确认。

### P1-4 拖完宠物等 400ms 再单击，便签不跟随宠物（本次未提交改动的回归）

**位置**

- `src/stores/noteStore.ts:931-936`：`setForm("note")` 用“当前宠物几何与 `st.petPos` 的差 > 4px”判断“是否被拖过”。
- `src/stores/noteStore.ts:796-814`：`autosaveGeometry` 在宠物态会把当前（吸附后的）宠物位置写回 `st.petPos` 并持久化。
- `src/App.tsx:187-196`：`onMoved` 400ms 防抖调用 `autosaveGeometry`。
- `src/components/PetStage.tsx:205-216`：拖拽由 `startDragging()` 交给 OS，落点由 `onMoved` 记录。

**机制（按时间顺序）**

1. 用户把宠物拖到新位置并松手。
2. 400ms 后，`onMoved` 的防抖触发 `autosaveGeometry`，把**拖动后的位置**写入 `st.petPos` 和 `config.pet_x/y`。
3. 用户再单击宠物，`setForm("note")` 读取当前几何，和 `st.petPos` 比较——两者相等，于是 `dragged = false`。
4. `expandToNoteForm(st.noteGeom, ..., null)` 走“没挪过”分支，便签回到**上一张便签的存档位置**，而不是宠物所在位置。

**实际表现**

- 拖完宠物**立即**（<400ms）单击，`autosaveGeometry` 还没来得及更新 `st.petPos`，`dragged = true`，便签会跟着宠物；超过 400ms 后再单击，行为反过来。
- 这正好与使用说明/计划里的 9b 预期相反：“拖到哪儿，便签就在哪儿展开”。用户等得越久越容易复现。
- 启动时如果宠物被 `snapToWorkArea` 夹回工作区（贴边配置、换显示器），`st.petPos` 仍是夹取前的位置，当前几何与它不同，又会被误判为“拖过”，导致便签按宠物锚点展开，9c 的“分毫不差”也可能失败。

**建议**

- 不要用“当前几何 vs 持久化 petPos”区分“拖没拖过”——`petPos` 会被自动保存更新，二者最终必然相等。
- 改用一个明确的标记：在 `PetStage` 的 `startDragging()` 时置 `petDraggedSinceCollapse = true`，在 `setForm` 展开/缩回完成后清掉；或者把“上一次缩回时的锚点”单独存起来，与当前宠物位置比较。
- 修完后按计划 §12.1 的 9a/9b/9c 用真手复验，并补充“等待 1 秒再单击”的用例。

**状态**：静态确认；属于未提交改动，v0.2.5 发布包不含此代码，不能按现状直接发下一版。

### P1-5 本地文件链接被 Milkdown 清洗成空 `href`，宣称的“单击打开本地文件”不可用

**位置**

- `src/components/NoteEditor.tsx:16-32`：`resolveLocalPath` 只接受 `file://` 前缀或盘符绝对路径。
- `src/components/NoteEditor.tsx:88-112`：点击监听只处理 `a[href]`，`href` 为空时直接返回。
- `node_modules/@milkdown/preset-commonmark/src/mark/sanitize-href.ts`：`SAFE_PROTOCOLS` 仅包含 `http:`、`https:`、`mailto:`、`tel:`、`ftp:`。
- `node_modules/@milkdown/preset-commonmark/src/mark/link.ts` 的 `toDOM`：最后一步把 `href` 设为 `sanitizeLinkHref(mark.attrs.href)`。
- 安装版本：`@milkdown/preset-commonmark@7.22.3`（`npm ls` 确认所有 Milkdown 包共用同一版本）。

**机制**

- `file:///D:/foo.pdf` 的 scheme 是 `file:`，不在白名单 → `sanitizeLinkHref` 返回空字符串。
- `D:\foo.pdf` / `D:/foo.pdf` 会被正则识别为 scheme `D:` → 同样返回空字符串。
- 渲染出的 `<a>` 的 `href` 是 `""`；`NoteEditor` 读到的也是空字符串，`resolveLocalPath("")` 返回 `null`，所以既不会调用 `openPath`，也不会 `preventDefault`。
- 普通外部链接（`https:`）会被保留，但代码也不会接管（见 P2-8）。

**后果**

- README v0.2.5 更新日志里“编辑器内指向本地文件的链接改为单击用系统默认程序打开”的功能当前无法工作。
- 对 `href=""` 的链接，浏览器默认行为可能是导航到当前文档（重新加载 WebView），相当于一次隐式刷新：可能丢光标、触发一次 `init_daily`（一次启动只结算一份旧委托，见 P1-2）、打断未落盘编辑。
- 相对路径（如 `./foo.pdf`）也不会被 `resolveLocalPath` 识别，默认导航到不存在的资源。

**建议**

- 链接点击统一在编辑器内拦截：`preventDefault()` 之后按 scheme 分流——`http/https` 用 `openUrl`，本地路径用 `openPath`，其余不处理。
- 要保留本地路径，需要在 Milkdown 层面覆盖 link schema 的 `toDOM`（或给链接增加 `data-href` 属性）绕过 `sanitizeLinkHref` 对 `file:`/盘符的清洗；清洗函数是安全更新，不能简单整体禁用。
- 修复后按 P3-10 的建议限制 `openPath` 的扩展名/路径，避免让便签里的链接直接执行 `.exe`/`.bat`。

**状态**：依赖源码确认；建议在真机上点一次 `file:///...` 链接复核。

### P2-4 `autosaveGeometry` 与 `setForm` 的几何持久化竞态

**位置**

### P2-5 隐藏启动/最小化时宠物解码与动作调度仍在跑

**位置**

- `src-tauri/src/lib.rs:2710-2712`：`--startup` 只跳过 `window.show()`，没有广播 `pet-visibility-changed(false)`。

- pause effect 不要用“值没变就返回”的写法处理首次挂载；首次挂载也要按当前 `mediaPaused` 决定是否暂停。

**状态**：逻辑确认；实际 CPU 受 WebView2 对隐藏窗口的节流影响，需实测任务管理器。

### P2-6 持久化失败被吞掉，结算可能出现“标记已结算但奖励没到账”

**位置**

- `src-tauri/src/lib.rs:854-858`：`save_config` 用 `write_config_atomic(...).ok()`，完全忽略错误。
- `src-tauri/src/lib.rs:63-67`：`write_index` 用 `fs::write(...).ok()`。
- `src-tauri/src/lib.rs:277-285`：`settle_previous_note` 先把目标标记 settled 并写索引，再 `load_config` 加余额并 `save_config`。
- `src-tauri/src/lib.rs:592-599`：`delete_note` 删除文件也忽略错误。

**机制**

- 磁盘满、目录只读、杀软占用、并发写冲突时，写配置/索引失败，但命令仍按 `Ok` 返回；前端显示保存成功。

- 删除便签时文件删除失败、索引删除成功，留下不可见的孤儿文件。

### P2-8 外部链接与相对链接没有被接管

**位置**

- `src/components/NoteEditor.tsx:91-112`：只对 `resolveLocalPath` 返回非空的链接 `preventDefault`；其余链接保留默认行为。
- Tauri 2.11.3 默认没有设置 navigation handler（除非业务代码 `on_navigation`），WebView2 会按自己的规则处理 `<a>` 导航。

**机制**

- `https://...` 链接不会被 `openUrl` 交给系统浏览器；在可编辑的 ProseMirror 里可能点击无效，也可能直接让主 WebView 导航到该网页，具体取决于 WebView 对 contenteditable 链接的默认处理。

**后果**

- 用户点链接后可能回不到应用界面（需要重启），或链接完全没反应；相对链接还可能触发一次 WebView 重载，放大 P0-1/P1-2 的风险。

**建议**

- 在 `NoteEditor` 的 capture 点击处理器里对所有 `.ProseMirror a[href]` 执行 `preventDefault`，按 scheme 分流：http/https/mailto 用 `openUrl`，本地路径用 `openPath`，相对路径不处理并提示。
- 也可以给 WebView 加 `on_navigation`，阻止应用窗口被外部页面替换。

**状态**：代码路径确认；WebView 的具体点击行为需真机复核。

### P2-9 副屏/自动隐藏任务栏时，普通最大化窗口会被当成“全屏”

**位置**

- `src-tauri/src/lib.rs:1086-1089`：`rect_covers_monitor` 只比较窗口矩形是否覆盖显示器矩形。
- `src-tauri/src/lib.rs:1173-1225`：`foreground_fullscreen_internal` 读取前景窗口的 `GetWindowRect` 和显示器 `rcMonitor`。
- 单测 `src-tauri/src/lib.rs:2194-2205` 假设“普通最大化窗口的右下角不覆盖屏幕”。

**实测**

- 本机主屏 1600×1000、任务栏可见、工作区 1600×952；WinForms 最大化窗口矩形为 `(-8,-8)-(1608,960)`。
- 因此主屏有任务栏时，`bottom = 960 < 1000`，**不会**误判（现有单测的假设在主屏成立）。

**风险**

- 副屏通常没有任务栏，工作区等于整块显示器；最大化矩形同样会向外多 8px，`bottom >= 显示器 bottom`，于是普通最大化的浏览器/编辑器会被当作全屏。
- 主屏把任务栏设为“自动隐藏”时也一样。此时用户只要最大化任何窗口，宠物就会隐藏，且每次轮询都保持隐藏。

**后果**

- 多屏用户可能觉得“宠物在我最大化浏览器时消失了”，但并没有游戏/投屏全屏。

**建议**

- 结合 `GetWindowPlacement`（`SW_SHOWMAXIMIZED`）或窗口样式区分最大化与真全屏；或使用 `SHQueryUserNotificationState`（`QUNS_BUSY`/`QUNS_RUNNING_D3D_FULL_SCREEN`）。
- 至少排除“最大化且带标题栏/边框”的普通窗口；把单测扩充为副屏、无任务栏、自动隐藏任务栏三类。

**状态**：主屏实测；副屏风险为逻辑推理，建议真机复验。

### P2-10 每次保存桌宠设置都会让便签重新展开/落位

**位置**

- `src/App.tsx:121-136`：监听 `ui-state-changed` → `fetchUiState`。
- `src/stores/noteStore.ts:754-790`：`fetchUiState` 在 `prev === "note" && noteGeom` 时仍会调用 `expandToNoteForm`。
- `src/components/SettingsPanel.tsx:68-75`：桌宠草稿每 400ms 调一次 `setPetConfig`。
- `src-tauri/src/lib.rs:1024-1046`：`set_pet_config` 每次都 emit `ui-state-changed`。

**机制**

- 或在 `setPetConfig` 的广播载荷里带上变更字段，前端按需处理。
- 加入 `formBusy` 检查。

**状态**：静态确认。

### P2-11 延迟的宠物气泡会在便签态弹出；启动时两条 say 互相顶掉

**位置**

### P2-13 闹钟间隔没有上限，超过约 24.8 天会触发定时器溢出

**位置**

- `src/components/SettingsPanel.tsx:260-267`：`<input type="number" max={1440}>`，但 HTML 的 `max` 不阻止用户输入更大的值。
- `src/stores/noteStore.ts:674-686`：`setAlarmInterval` 只做 `Math.max(1, Math.round(minutes))`，没有上限。
- `src/stores/noteStore.ts:402-406`：`setInterval(runCycle, Math.max(60_000, intervalMs))`。
- `src-tauri/src/lib.rs:1292-1296`：后端也只 `seconds.max(1)`。

**机制**

- JS 定时器最大延迟约为 `2^31-1` ms（24.8 天）。用户输入 `999999` 分钟时，`intervalMs` 远超上限，浏览器会按上限/极小值处理，`setInterval` 可能变成连续触发。

**后果**

- 用户输入一个看似合理的“很大值”就可能把闹钟变成刷屏；需要重启或改配置恢复。

**建议**

- 在 store、Rust 命令和输入框三处统一限制上限（例如 1440 分钟），并在输入时纠正。
- 对 `NaN`/空值也做兜底。

**状态**：静态确认；输入极端值可复现。

### P2-14 `hasPendingEdit` 的两类错误：失败后永久为 true、旧保存清掉新编辑

**位置**

- `src/components/NoteEditor.tsx:144-157`：每次输入 `setState({ hasPendingEdit: true })`；保存成功才置 false；`catch` 里只设置“保存失败”文本。
- `src/stores/noteStore.ts:922`：`setForm` 在 `hasPendingEdit` 为 true 时拒绝缩回。

**问题 A：保存失败后永久阻塞缩回**

- 磁盘满/文件被占用导致 `save_note` 失败，`hasPendingEdit` 保持 true；之后所有自动/手动缩回都被 `setForm` 拒绝，直到下一次编辑成功保存。
- 内容确实还没落盘，保留便签是对的；但没有重试、没有“另存/重试”入口，用户只能继续编辑或重启（可能丢内容）。

**问题 B：旧保存完成会把新编辑标记清掉**

- 输入 A 触发保存 A（500ms 后开始写盘）；写盘期间用户继续输入 B，`hasPendingEdit` 又被置 true。
- A 的 `await` 完成后无条件 `setState({ hasPendingEdit: false })`，此时 B 还没保存，但便签已经允许缩回。
- 因为编辑器保持挂载，B 的定时器最终仍会保存，通常不丢内容；但“正在编辑时不缩回”的承诺失效，遇到退出/崩溃时会丢 B。

**建议**

- 用单调版本号/编辑序号：每次输入递增，保存完成只在版本号未变时清标记。
- 保存失败时保留标记并提供重试；可把待保存内容留在 store，退出前 flush。

**状态**：静态确认。

## 10. 追加修复（用户真机反馈，2026-10-21）

### 10.1 桌宠几乎只演叹气/写字，金袋和偷吃零食不出现

**现象**

- 用户观察：动作基本只有 `mood-sulk`（叹气）和 `mood-work`（写代码），`mood-coins`（金袋）与 `mood-snack`（偷吃零食）几乎不出现。

**原因**

1. `PetStage.nextIdle()` 只调用 `pickWeighted("Idle", ...)`；而 `mood-coins`、`mood-snack` 在清单里的 `Pool` 是 `Notify`。代码里没有任何一处挑选 `Notify` 池，这两个动作是**死配置**，永远不会被选中。
2. `mood-snack` 还有 `Gate: empty_note`：只有“明日委托”没填时才是候选；`mood-coins` 有 `Gate: settled`，只在结算后的 **3 分钟**内有效。即使调度给了机会，金袋也容易被错过。
3. `mood-sulk`（权重 120）和 `mood-work`（80）本身就在 `Idle` 池里，且都是一次性显眼动作；`idle-breath` 是常驻呼吸，感知上会被当成“没动作”，所以看起来只剩叹气/写字。

**修复**

- `pickWeighted` 支持传入多个池；`nextIdle` 改为 `pickWeighted(["Idle", "Notify"], ...)`，`Notify` 按权重和 Gate 混入常规轮换。`mood-snack` 在明日委托为空时会周期性出现。
- `PetStage` 监听 `settledAt`：结算后宠物可见时，在入场请安约 2 秒后补演一次 `mood-coins`；用模块级 `coinsSettledAt` 保证同一次结算只演一次（跨展开/缩回也不重播）。窗口隐藏则等恢复可见且仍在 3 分钟门控内再补。
- README/使用说明原本就写了“刚结算/明日委托是否填写会改变动作”，这次修复让实现与文档一致。

**说明**

- 如果明日委托已经填了，`mood-snack` 不会出现，这是 Gate 的设计，不是 bug。
- 金袋只在“本次结算有原石/摩拉奖励”且 3 分钟内可见时播放；如果结算后一直藏着宠物，超过 3 分钟就不会补演。
- 闸门：`tsc` 通过、`npm run build` 通过；`mood-coins`/`mood-snack` 的实际观感需真机确认。

### 11.1 追加：缩回宠物时的请安会把金袋冲掉（真机反馈，2026-10-22）

**现象**：勾委托只可能发生在便签态，而便签态不渲染 `PetStage`（`App.tsx:470` 的 `form === "pet"`；形态切换本身是 CSS 折叠，`NoteEditor` 不卸载，保存照跑）。于是「完成了」这件事必然在宠物组件不在的时候发生，等缩回宠物时先演的是入场请安，金袋既没演、增量也已经被吞掉——主人永远看不到金袋。

**根因两条**

1. 入场那趟没有参照系：基线原先是 `PetStage` 里的模块变量，只有宠物挂载过才会被写入。本次运行从便签态起手的，缩回时基线仍是 `null`，`pending` 判定直接为 false。
2. 增量被静默消费：`checkedCount` 变化时若宠物不可见/未挂载，旧写法照样把基线推到新值，这份「新完成」就永久丢了。

**修复**（按用户提的规则：没有新增完成 → 请安；有新增 → 金袋）

- 基线改为 store 字段 `noteStore.checkedBaseline`，由 `fetchProgress` 锚定：本次运行第一次拿到进度就写下当前条数；条数**变少**（跨天新建、取消勾选）时立刻重新对齐——不允许出现基线高于现状、因而永远比不过「新增」的死局。
- 入场统一走 `playEntry()`：`checked_count > checkedBaseline` 就播 `mood-coins`，否则播 `greet-bow`，然后把基线写成当前值。挂载 effect 与「隐藏启动后第一次可见 / 还欠一次新完成」的 unpause 分支都用它。
- 在场时的增量仍由 watch effect 接手，与 `playEntry` 共用同一条基线（effect 声明顺序保证入场先消费，不会重播）。**演不成的几种情况（隐藏中、8 秒冷却内、素材缺失）一律不消费基线**，留到下一次可见或下一次入场补演。
- `lastCoinsAt` + `COINS_COOLDOWN_MS`（8 秒）保证金袋不被剪回第一帧。

**闸门**：`tsc` / `npm run build` / Prettier 全过。真机待确认：便签里勾一条 → 缩回宠物，第一眼应是金袋而不是请安；再展开→缩回（中间没勾新的）应回到请安；勾在「随手小记」里的项不计入完成数，不会掉金袋（设计如此）。

顺带：`progress_of` 的委托条目改为共享的 `items()` 迭代器，`section_complete` 的勾选判定抽出 `is_checked_item`；Rust 测试 `progress_of_matches_settlement_semantics` 按新语义重写，并补 `section_has_content_ignores_placeholders_and_fences`（**45 项全过**）。README 与使用说明的「她会看你的数据」表同步改写。

**闸门**：`cargo test` 45 通过、`tsc --noEmit` 通过、`npm run build` 通过、Prettier 已跑。真机待确认：勾一条委托是否半秒内掉金袋、21 点没做完是否叹气、5 分钟不理是否打招呼、呼吸是否不再被当成「换段」。

## 12. 金袋改成事件驱动（§11.1 的两版补丁都不生效，2026-10-22）

§11.1 那版「基线挪进 store + fetchProgress 锚定」在真机仍然只演请安。静态排查把能排除的都排除了：`target/debug/…exe`（20:04 那次编译）里确实带 `checked_count` 字符串，字段名不是 camelCase；`save_note` 在 22:56:13 真的写了 `.md`（索引 mtime 停在 09:03 是因为正常保存**故意**不重写索引，见 P1-2 那条修复），`fetchProgress` 只在 save 成功后被调用一次。也就是说**Rust 侧的数据是对的，出问题的是「前端事后推算增量」这件事本身**：保存、`fetchProgress`、缩回入场三条异步路径的先后顺序没有保证，任何一版基线算法都会有某条交错把增量吃掉——继续加判据只是给竞态打补丁。

改成事件驱动，判定放回唯一知道前因后果的地方：

- **Rust**：`save_note` 已经读到了旧正文（做「内容未变化就跳过」用），顺手 `progress_of(旧).checked_count` 与 `progress_of(新).checked_count` 比较，变大就 `app.emit("task-completed", 增量)`。同一次保存里判定，不存在顺序问题。
- **前端**：`App.tsx` 监听 `task-completed` → `noteStore.coinsPending = true`（布尔即可，连着勾几条也只欠一次）。`coinsPending` 是 store 状态，跨 `PetStage` 卸载存活。
- **桌宠**：`playEntry()` 见 `coinsPending` 就演 `mood-coins` 并把账清掉，否则演 `greet-bow`；在场时收到事件由 watch effect 立刻补演。8 秒内的第二次不重播（`COINS_COOLDOWN_MS`），那种情况下账继续欠着，等下一次入场或可见性翻转兑现。
- 于是 §11.1 的 `checkedBaseline`、ratchet 对齐、`pendingCheckIns()` 全部删除，`fetchProgress` 回到只做 `set({ progress })`。

**闸门**：`cargo test` 45、`tsc`、`npm run build`、Prettier 全过。

## 15. 修复：dev 下勾选委托后缩回宠物只演请安、不出金袋（2026-10-23）

**根因**：`playEntry` 在**同步阶段**就把 `coinsPending` 写成 `false`（旧 `PetStage.tsx:215`），而真正出画要等 `loadeddata`。dev 的 `<React.StrictMode>`（`main.tsx:19`）会对每个新挂载的组件跑「挂载 → cleanup → 挂载」：第一趟读到账并清掉、`play` 被 cleanup 的 `generation += 1` 作废（金袋一帧未出），第二趟读到的已是 `false` → 走 `??` 兜底的请安。生产版无 StrictMode 故不复现；但同一形状的丢账在生产也存在（入场解码途中被全屏避让置 `mediaPaused`，`generation` 同样作废）。

**修法**：把「消费」从意图后移到确认出画。

- `play(action, opts?: { payCoins?: boolean })`：在 `start()` 里把 `el.play()` 改成 `.then(...)`，**且 `gen === generation.current` 时**才 `setState({ coinsPending: false })`。被作废 / 自动播放被拦 / 解码失败都不算演过，账留着等下次入场。
- `playEntry` 与「在场补演」effect：删掉同步 `setState`，但**保留 `lastCoinsAt.current = Date.now()` 的同步写入**——它不只管 8 秒冷却，还负责压掉同一次挂载里被 `playEntry` 和补演 effect 演两遍（`coinsPending` 这个 prop 在同一拍里仍是旧值）。两处 `play` 都传 `payCoins`。
- `cleanup` 未改：`generation` 本来就能同时作废 `start()` 与新加的 `.then`。

**闸门**：`tsc --noEmit`、`npm run build`、Prettier 全过（`AGENTS.local.md` 与 `docs/桌宠化重构计划.md` 的格式告警为既有，未处理）。**真机待确认**：dev 下勾选 → 缩回演金袋且不重播；8 秒内再勾一条 → 缩回演请安、账留到下一次入场；缩回瞬间被全屏避让再回来也能补演金袋。
